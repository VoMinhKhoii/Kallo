# Group Tracking — Decision

> Generated by the explore→decide workflow (16 agents). Source of truth for the build is [group-tracking-plan.md](./group-tracking-plan.md).

## Winner
**Circle (Locket-style global friends) — shipped as the MVP, with a reserved cohort-container seam grafted from Crews/Hybrid and a public_profiles projection table grafted in to close a leak all three designs share.**

## Why
Circle wins on three of the four hard constraints decisively and ties on the fourth, and the one lens where it loses (coach-container) is the most deferrable.

1) Text-first hero — TIE. All three put zero camera at/before input, share is strictly post-save, and the shareable object is a TEXT-derived Macro Card. Verified in-repo: no @vercel/og, next/og, satori, or navigator.share exists today, so the artifact is net-new and byte-identical across all three. It does not differentiate. (Confirmed by the Product judge and by grep.)

2) Genuine visual vividness — TIE-to-Circle-edge. Same Macro Card + Weekly Wrapped for all. The vividness DIFFERENTIATOR is friction-to-first-vivid-moment: Circle's add-by-@handle + ambient auto-broadcast cures the beta "lacks vividness" complaint the instant ONE friend logs, with zero setup by the viewer. Crews requires name-group → mint-code → get-someone-to-redeem (three gates) before anything is vivid — a cold-start death. (Product judge: Circle 9 vividness vs Crews 5.)

3) Safe + affordable on the existing stack — Circle WINS. Verified: existing meals RLS is exactly USING (auth.uid() = user_id) with meal_items inheriting via EXISTS-through-meals, and all three correctly mirror it with additive OR'd policies. Circle has the FEWEST tables, ONE symmetric relationship (friendships) with a canonical user_low<user_high invariant that structurally kills duplicate/asymmetric rows, and its hardest read path is a single pairwise SECURITY DEFINER EXISTS — a pattern the repo already uses safely (handle_new_user is SECURITY DEFINER with pinned search_path, confirmed in 20260224100032). Critically, Circle is invisible-by-default: a meal needs an EXPLICIT meal_shares row AND an accepted friendship to be seen, so a friend with no share row still sees zero — the safest possible default (opt-in to exposure). Crews ships mealVisibilityDefault='group' (opt-OUT, its own design + two judges flag as debatable) and a two-way group_members self-join + soft-leave left_at filter + COALESCE visibility resolution — the single most leak-prone policy of the three. Hybrid is self-described 'high' cost with the largest surface and dead coaching schema. (Eng judge: Circle 8 safety vs Crews 5 vs Hybrid 4.)

4) Extends cleanly to coach→client — Circle is SUFFICIENT, not best, and that's acceptable. Circle already ships coach_assignments (directed coach→client, rank primary|secondary, partial-unique 1-active-primary-per-client) and an OR'd is_active_coach_of() branch in the same meals SELECT policy — so the coach console is a UI/route addition, not a data rebuild. The ONLY thing Circle lacks is a named cohort 'space' object for a coaching BUSINESS (group programs, cohort recaps, owner→manager→coach orgs). But coaching is post-MVP for ALL three designs, so a missing container is a deferred-feature gap, not a now-blocker — and it is exactly what grafting fixes (reserve an audience/group key now, build the container later). Choosing Crews to get the container would trade a certain cold-start virality failure NOW for a coaching convenience LATER, the wrong trade for a product whose stated pain is consumer vividness/adoption.

Decisive synthesis: 2 of 3 judges pick Circle; the Coach judge picks Crews but explicitly says (a) Circle has the safest trust posture, (b) Crews' lone weakness is a one-line default flip, and (c) Crews' container advantage is for a business mode that ships later. Hybrid is dominated on every lens (highest cost, largest leak surface, IA confusion, 'risk of shipping nothing'). So: ship Circle, GRAFT the container-as-reserved-seam from Crews/Hybrid, GRAFT the opt-in-per-meal safety the Coach judge praised (already native to Circle), and GRAFT the public_profiles projection-table fix that NONE of the three fully addressed (verified: user_profiles co-locates weight_kg/tdee_kcal/calorie_target under owner-only SELECT — reading display_name/handle cross-user from that table would leak body metrics).

## Candidate designs compared

### Crews
- **One-liner:** Named, explicitly-joined groups (Gym bros, Family, later a coaching cohort) with a group-scoped meal feed — a "group chat for meals" where membership is the unit of trust, RLS reads through group_members, and a coaching cohort is just a Crew where one member holds a coach role.
- **Cost:** medium
- **Pros:** Membership is the unit of trust, so RLS is a clean EXISTS-through-group_members join that mirrors the codebase's existing child-table pattern — leakage is structurally impossible for unrelated users, not app-enforced.; Coach-ready from day one with near-zero extra surface: a cohort is just role='coach' + a dormant assignment table and a dormant policy that ship now and activate later — social→coaching is an extension, not a rebuild.; Multi-Crew membership works without duplicating meals (no group_id on meals); visibility resolves through override-then-default, so the same log can be Family-only, Gym-bros-shared, or private per the user's intent.; Honors every health guardrail by construction: no group_id leakage of body weight (separate table never joined), no vanity metrics, no global feed, private reactions only — and the Macro Card gives Strava-grade virality with zero photography and zero Storage.; Clean web/mobile parity: REST `/api/v1/groups/*` over pure functions is the single contract, auth already unified, realtime shareable, event shape future-proofed for push.
- **Cons:** Heaviest data model of the three formats (5 new tables + 2 profile columns) and the most RLS policies to author and test — higher up-front cost than a lightweight global-friends format.; Explicit create/join friction: unlike a zero-config global friend circle, users must name a Crew and share a code before anything is social — the feed is empty until that work happens (mitigated by the tracker being independently valuable).; An audience/visibility decision per Crew (and optional per-meal override) adds 'which Crew?' overhead that the competitor-mechanics brief warns against for the pure-consumer layer — Crews trade some of that intimacy-simplicity for explicit structure and coach-readiness.; The 2-way self-join visibility policy is the most complex RLS in the schema and the easiest place to introduce a subtle leak or a performance cliff; demands the strongest test coverage.; Soft-leave + reserved-enum gymnastics exist purely to satisfy the append-only shared-preview constraint, adding incidental complexity that wouldn't exist with normal migrations.

### Circle (Locket-style global friends)
- **One-liner:** No group container — users add each other as mutual global friends by handle; logging a meal optionally broadcasts a text-first macro card to your whole circle as an ambient, like-free "what I'm eating" pulse, with a coach→client overlay reusing the exact same membership + visibility primitives.
- **Cost:** medium
- **Pros:** Honors the brief's hardest constraints natively: pairwise RLS makes friends-of-friends leakage structurally impossible, and the additive-policy approach never touches the existing 'own data' policies.; Coach-ready with near-zero extra cost — coach_assignments + meal_shares.visibility + the OR'd coach branch in the meal SELECT policy mean the coach console is a UI/route addition, not a data-model rebuild.; Zero Supabase Storage required for the entire v1 (feed, avatars, Macro Card, Wrapped) — ships with buckets still disabled, exactly as recommended.; Text-first moat is fully preserved: no camera at input, share is strictly a post-save act, and the shareable artifact is generated from text via next/og (no new dependency).; Reuses existing primitives heavily (persisted-meal-card aesthetic, calorie-ring, macro-bars, adherence-heatmap, Avatar fallback), keeping it on-brand and low-build.; Solo tracker stays independently valuable; only the social wall is empty pre-invite, avoiding Locket's useless-solo and BeReal's single-point-of-failure traps.; One clean REST contract (/api/v1/groups/*) backed by pure functions gives the mobile port a drop-in path without Server-Action or Metro coupling.
- **Cons:** No group container means no shared 'space' object — challenges, group recaps, or a family/household view would need a later `audience`-keyed grouping layer (the column is reserved, but the UI/queries aren't built).; 'Most-recent-per-friend' ambient wall is intentionally limited; users who expect a rich scrollable feed of friends' history will find it sparse by design.; citext + handles add a small PII/abuse/moderation surface with no tooling yet (block exists, but no reporting/admin review).; meal_shares as one-row-per-meal (not per-recipient) keeps it clean but means a future 'share to a subset of friends' would require schema change — acceptable since the consumer layer intentionally has no audience picker.; Realtime is deferred to polling for MVP, so 'friend just logged' updates have up-to-60s staleness on web until Supabase Realtime is wired.; next/og card rendering adds an operational concern (caching, rate-limiting) that the app doesn't currently have for image-type responses.

### Circle + Crews (Hybrid: global friends layer + optional scoped groups)
- **One-liner:** A global, mutual ~20-person Circle is the lightweight default — logging a meal ambiently broadcasts a TEXT-derived macro card to friends — with optional scoped Crews (family/gym/coaching cohort) layered on top via the SAME membership + role model, so the social layer ships first and the coach→client mode is a pure role/visibility extension, not a rebuild.
- **Cost:** high
- **Pros:** Best of both worlds: friends-first virality (low-overhead ambient broadcast, no audience picker) AND scoped structure for family/gym/coaching — captures the consumer loop without sacrificing the coaching business model.; Genuinely coach-ready from day one: role enum + coach_assignments + visibility override + the coach RLS policy all exist at launch, so coaching mode is UI-only later, never a schema rebuild.; Solo tracker stays fully valuable with zero friends/crew — only the social surface is empty until you invite, avoiding Locket's useless-solo trap and BeReal's single-point-of-failure.; Honors every health guardrail structurally: weight has no social column, default visibility is private, no leaderboards/likes, reactions private — leakage is prevented by construction, not by discipline.; Text-first moat intact: the shareable artifact is a TEXT-derived macro card, photos are optional post-hoc accents only, and there's no camera anywhere near the input.; Clean web+mobile parity via REST contract + Supabase Realtime + the pre-designed event shape; the macro card renders identically on both platforms from shared tokens.
- **Cons:** Highest implementation cost of the format options — two relationship systems plus coaching schema plus the OG card renderer is a large surface for v1; demands disciplined phasing to ship.; Largest RLS attack surface of any approach: more policies and helper functions means more places a leak can hide; requires the most rigorous positive/negative test coverage.; Conceptual overlap between Circle and Crews can confuse users ("why are my friends AND my crew both here?") — needs careful IA on the Groups surface (tab strip) and copy to keep the mental model clean.; Coaching schema present-but-dark is dead weight until the coach UI ships; carries maintenance and review cost for a feature not yet user-visible.; @vercel/og / satori adds a server-render dependency and font-loading (Lora + DM Sans with Vietnamese diacritics) complexity that must be validated for diacritic glyph coverage before launch.

## Grafted ideas (pulled into the winner)
1. From Crews/Hybrid: the reserved cohort-container seam. Ship a NULLABLE `audience_id uuid` column on `circle_events` (the brief's group_id slot) AND reserve an `org`/owner→manager→coach hierarchy by NOT consuming 'owner'/'admin'/'manager' role values now — so a later `cohorts` table (a named coaching space attaching programs, group recaps, billing) bolts on without an ALTER. This converts Circle's one real weakness (no business container) into a deferred extension instead of a rebuild.
2. From the Engineering judge (affects all three, fully addressed by NONE): a separate `public_profiles` projection table instead of adding display_name/handle to `user_profiles`. Verified in-repo: user_profiles co-locates weight_kg, tdee_kcal, calorie_target under a single owner-only SELECT policy, so any cross-user read of a social identity column risks leaking body metrics. public_profiles holds ONLY {user_id, handle citext unique, display_name, avatar_seed} and gets its own cross-user SELECT policy; user_profiles' owner-only policy is never loosened. This is the single most important graft and it is winner-independent.
3. From Crews/Hybrid: warm/sage-terracotta compliance tags and 'nudge-from-the-log' as the coach interaction idiom (never cold red), reusing meal_visibility_overrides/meal_shares for per-log scoping — adopt verbatim for Circle's later coach console so coaching feels on-brand, not clinical.
4. From Crews: the partial-unique 'one active primary coach per client' index and reserving rank='secondary' — already present in Circle's coach_assignments; keep it explicitly so multi-coach orgs need no migration.
5. From all three: the per-card derived dish-color swatch / category glyph (one illustration style, warm appetite tones) seeding both the feed card and the avatar via avatar_seed — gives vividness with zero upload, reinforcing the no-photography moat.
6. From Crews/Hybrid: the soft, OPTIONAL reciprocity blur ('friends' cards softly blurred until you've logged today') framed as behavior-encouragement, never BeReal's hard lock — opt-in per user.
7. From the Product judge's caveat (a real risk, not a feature): ship a reserved-handle blocklist + friendships.status='blocked' path from day one to blunt the @handle impersonation/squatting surface that add-by-handle introduces, and keep the ambient wall strictly most-recent-per-friend / non-scrollable so it never drifts into the forbidden global newsfeed.

## MVP scope
BUILD NOW (the minimum vivid, viral, safe slice):
1. public_profiles table + RLS + reserved-handle blocklist (the leak fix — non-negotiable, winner-independent).
2. friendships table + RLS + add-by-@handle search, request/accept, block, copy-link invite via sonner toast. REST: POST /api/v1/groups/friends/request, /accept, GET /friends/search?handle=.
3. meal_shares table + RLS + the additive meals AND meal_items SELECT policies + the SECURITY DEFINER helpers (is_accepted_friend; ship is_active_coach_of too — it's a dormant OR branch, costs nothing). Share toggle ON persisted-meal-card.tsx (post-save only).
4. Circle home: ambient, non-scrollable, most-recent-per-friend wall reusing persisted-meal-card aesthetic. Nav entry + empty state.
5. Macro Card OG route (net-new @vercel/og dependency; 9:16 from text) + OS-native share. This is THE growth artifact — ship it, not a stub. Cache per shareId + rate-limit.
6. circle_events table + insert trigger; consume via TanStack refetchInterval polling (Realtime deferred).
7. Both-directions RLS test suite as a merge gate.

SHIP SCHEMA-ONLY, UI DARK (so coaching never gates launch):
- coach_assignments table + RLS + the dormant coach OR-branch in the meals policy (already in #3). No coach console UI, no writes to the table.
- circle_events.audience column + coach_assignments.audience_id column reserved (the grafted cohort seam) — present, unused.

EXPLICITLY DEFERRED (do NOT build now):
- Weekly Wrapped recap card (second OG render) — fast-follow after Macro Card proves out.
- Coach console (app/.../groups/coach/) — post-MVP; data model is ready so it's UI + a thin REST add, not a rebuild.
- Named cohort/household/org CONTAINER (cohorts table, owner→manager→coach hierarchy, group recaps, billing) — the grafted Crews capability; reserved via audience keys, built when coaching-as-business is greenlit.
- Supabase Realtime subscriptions — MVP polls; graduate once event volume is understood (config.toml Storage stays disabled too).
- Real photos — ship-last-or-never; the only thing requiring a Storage bucket.
- Reactions table — private emoji reactions are post-MVP; ship the wall read-only first.
- Soft reciprocity blur — optional, post-MVP toggle.
- Mobile — later parity follow-up against the same /api/v1/groups/* contract; not blocked on.

## Open questions
1. public_profiles exposure scope: should cross-user SELECT be open to ALL authenticated users (enables @handle search of anyone) or restricted to accepted-friends/pending-requesters only? Open search is needed for add-by-handle to work, but it leaks the existence + display_name of every handle. Likely answer: handle is searchable by exact match only (not enumerable/prefix), display_name + avatar_seed returned only after a request exists — needs a decision before writing the search RLS.
2. Reserved-handle blocklist + impersonation: what's the v1 list and is there ANY reporting/admin-review path, or only self-serve block via friendships.status='blocked'? The Product judge flagged this as a real adoption risk; we have no moderation tooling today.
3. Ambient wall cap: 'most-recent-per-friend' — what is the hard cap (e.g. top 20 friends, last 24h) that keeps it structurally non-scrollable and prevents drift into the forbidden global newsfeed? Needs an explicit number.
4. Macro Card cost/caching: confirm @vercel/og render latency + cost on the current hosting (Cloud Run, per memory), set the immutable-per-shareId cache TTL and rate-limit, and validate Lora + DM Sans Vietnamese-diacritic glyph coverage in satori before launch — diacritic dropouts would break 'bún chả'.
5. Cohort-container timing: do we build the reserved cohorts table now (schema-only, like coach_assignments) or leave it as just the audience_id/audience columns until coaching-as-business is greenlit? Leaning fully deferred to avoid dead-weight maintenance, but confirm.
6. Friend-request growth loop: copy-link invites land non-users on a signup page — what's the post-signup auto-friend behavior (auto-accept the inviter? pending request?) and does that create any consent/abuse edge?
7. Default share scope on the toggle: confirm meal_shares defaults to 'private' and the share toggle is a deliberate per-meal opt-in (matching Circle's safety posture), with no per-friendship 'always share' shortcut in v1 that could re-introduce opt-out exposure.
