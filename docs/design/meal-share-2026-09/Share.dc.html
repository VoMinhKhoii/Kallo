Proposed. G9 the identical portion bar — one implementation of the rule, two renderers. Keyboard: ← → move 5%, ⇧← ⇧→ move 1%, Home/End clamp, role="slider" with aria-valuetext “Bạn 65 phần trăm”. A real dialog footer, so the consequence line and the escape hatch sit where a desktop user expects them.

What is wrong today
1

The action is unlabelled and ambiguous. Five bare icons; “offer this meal to a friend” (user-plus) sits three slots from “broadcast to my circle” (users). Two different sharing concepts, one row, no words.

2

No subject. Neither the sheet nor the dialog names the meal being shared. On web the card is behind a scrim; on mobile it is off-screen entirely.

3

Mode is two web cards. A 2-up grid of label+hint boxes is a web pattern. iOS reaches for a segmented control — and the app already ships one (SegmentedStrip, the pill track on the scan toggle).

4

The CTA scrolls. Sheet body and button live in one SingleChildScrollView, so with a long friend list the primary action drifts off the bottom. Native sheets pin it.

5

The portion story is one sentence. “Mỗi người nhận 1/2 phần” — no scale, no numbers, no sense of a dish being divided.

6

An irreversible act, unannounced. A split rescales your already-logged meal in place, and the server then refuses to ever split it again (portionFactor < 1). Nothing in either UI says so before you commit.

7

The portion label cannot count. _portionLabel is 1/(1/factor).round() — fine for even splits, wrong the moment a factor is not a unit fraction. 0.35 prints “1/3”.

8

No feedback vocabulary. No press states, no haptics on mobile (raw GestureDetector + Opacity); on web, “Đang tải…” as a loading state where mobile ships a skeleton.

9

No result preview. You press a brown button and find out afterwards what happened to your own diary. Copy and split — one reversible, one not — look identical up to the label.

What changes underneath

The UI above needs exactly one new idea on the server, and it is backward-compatible by construction.

A

One optional number on the wire. shareMealWithFriendsSchema gains myPortion: number (0.1–0.9), accepted only when mode = 'split' and exactly one recipient. Absent → today’s 1/(N+1) path, untouched.

B

Sender scales to their own share. scaleOwnMealInPlace(tx, source, items, myPortion) — the function already takes an arbitrary factor. The invite records portion_factor = 1 − myPortion for the label.

C

Accept needs a ratio, not a fraction. Today accept copies verbatim because an even split leaves both shares equal. Uneven breaks that. Add meal_share_invites.copy_factor = recipient’s share ÷ sender’s remaining share, default 1 — so every existing row and every even split keeps byte-identical behaviour, and no backfill is needed.

D

One type widens. copyMealVerbatim’s factor: 1 | 0.5 becomes factor: number. The body already multiplies generically; the literal union is the only thing in the way.
